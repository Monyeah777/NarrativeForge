# NF ターミナル（`nf shell`）——デスクトップシェル退役後の人機入口

> 最后更新：2026-10-03 (last updated)

> ⛔ 操作指示：本ファイルは直接実行できるコマンドと判定を含む。読んだら実行せよ。資料として読むな。

## このターミナルとは

NF デスクトップ GUI シェルは 2026-09-09 に恒久退役し（記録は `L3_FROZEN.md`）、公開面は「プロトコル + core ライブラリ + CLI」に収束した。人機インタラクション面はこれで空白となり、`nf shell` が埋めるのはまさにこの層である：**既存の** CLI コマンド面を能力メニューとして対話セッションに編成する——1 行読む → 解析 → ゲート → 分派 → 印字。

三つのハード制約（リポジトリのレッドラインと同源）：

1. **サードパーティ依存ゼロ**：Python stdlib のみ。curses（Windows に存在しない）と GUI ツールキットは使わない。
2. **決定性**：同じ入力なら 2 回の実行がバイト単位で一致する（`--exec` が回帰面）。
3. **安全ゲート**：書き込み系コマンドは既定で実行を拒否し、明示的な確認（対話での yes 入力、または明示的な `--yes`）を要する。

## 最速の始め方（2 コマンド）

```sh
./scripts/nf                       # POSIX：引数なしで対話ターミナルに入る
python scripts/nf.py shell         # クロスプラットフォームの等価な書き方（Windows では scripts\nf.cmd も可）
```

三つの起動経路の位置づけ（**混用するな**）：`scripts/nf`（POSIX）は**デーモンのファストパス**を備え、`eval "$(nf daemon shell-init bash)"` と組み合わせればミリ秒級クライアントになる；`scripts\nf.cmd` にもファストパスがある（POSIX ランチャーより遅い）——cmd.exe にソケットが内蔵されていないため、`scripts/nf_client.py`（**純粋な stdlib**、`python -S` で起動、リポジトリのモジュールを import しない）がソケット往復を 1 回代行し、デーモンが取れなければ直接実行に退避する（POSIX ランチャーと同じ契約）；`python scripts/nf.py` は唯一の真源入口であり、前の二者はそのランチャーにすぎない。

入ったら：`0`–`8` を入力すると能力ゾーンの例が見られ、`/menu` でメニューを再表示、`/help` で使い方、`quit` で終了する。
任意のコマンドはそのまま直接通せる。例：`nf doctor`、`nf market --list`、`nf assemble "西幻生存"`。

## 能力メニュー（デスクトップシェルの七区 → CLI コマンド面）

| キー | 能力ゾーン | 対応するコマンド面（例） |
|---|---|---|
| 0 | 環境セルフチェック | `nf doctor` |
| 1 | ワンクリック世界デモ | `nf demo` |
| 2 | 要件 → アセンブリ計画 | `nf assemble "<需求>"` · `nf assemble … --check <成品.md>` |
| 3 | 全チェーン生産 | `nf run --pipeline <管线.md> --modules … [--seed]` |
| 4 | 検証と健診 | `nf lint` · `nf conformance` · `nf module verify` |
| 5 | シェルフとアセット | `nf market --list` · `nf asset ls` · `nf asset inventory` |
| 6 | パイプラインとモジュール | `nf pipeline new …` · `nf module ls` |
| 7 | ヘルプとコマンド面 | `nf --help` · `nf help <cmd>` |
| 8 | 書き込みフォーム | `/form <id>` の項目ごとの問い合わせ（13 表、後述の「書き込みフォーム」）——本ゾーンは**動作リテラルを持たない**：動作は `FORMS` から投影される |

メニューの真源は `desktop/src/core/terminal.py` の `ZONES` である；**メニューは実在するコマンドしか指してはならない**——verify check39 と `desktop/tests/test_terminal.py` が同じ判定を共有し 1 行ずつアサートする（`terminal.example_resolves`）。新しい能力は先に CLI に落ちてからメニューに登録する。ゾーンの**動作**も同様に真源から出る：明示的な `actions`、または（フォーム区では）`terminal.zone_action_dicts()` が `FORMS` から投影する。

## 対話構文

| 入力 | 挙動 |
|---|---|
| `0`–`8` | その能力ゾーンの説明とコピー可能な例を見る |
| `/menu` `/zone 4` | メニューを再表示 / あるゾーンの例を見る |
| `/find <词>`（`/search` は同義） | **全コマンド面**を検索（ヒットすればコマンド + 一行の用途、外れれば候補を出す） |
| `/commands [过滤]` | 到達可能な全コマンドを列挙（トップレベル + 第二階層、部分文字列で絞り込み可） |
| `/map [族或片段]` | **能力マップ**：全トップレベルコマンドを能力ファミリ別にキュレーションして提示（8 ファミリ）、絞り込み可 |
| `/complete <前缀>` · 行末 `Tab` | **補完**：コマンド / 第二階層サブコマンド / フラグ / スラッシュコマンド / 能力ファミリ接頭辞 |
| `/history [n]` | 履歴を見る（直近 n 件）；`quit` と Tab 行は履歴に入らない |
| `/set [k=v …]` | ビュー設定を変更（`color` / `width` / `limit`）；引数なしなら現在値を印字 |
| `/form [id]` | **書き込みフォーム**：id なしなら全件列挙；id ありなら項目ごとの問い合わせを開始（パラメータを揃える → コマンドを組み立てる → 二次確認） |
| `/cancel` | 進行中のフォーム / 動作を中止（ディスクへの書き込みは一切しない） |
| `/help` または `/help <cmd>` | CLI ヘルプ面へ転送（`nf help …` と等価） |
| `nf <args…>` または `<args…>` | CLI へ直接通す（`nf` 接頭辞は省略可） |
| `quit` `exit` `q` `退出` | セッションを終了 |

堅牢性（一流 CLI ターミナルの定番いくつか）：**Ctrl-C は現在行を取り消すだけで、セッションは殺さない**；行末の `\` で**行継続**（複数行コマンド）；行内の `#` でコメント開始（引用符内の `#` は保持）；コマンドを打ち間違えたら**タイポ候補**（編集距離 ≤3）を出し、60 コマンド分の usage を顔面に投げつけない。

## コマンド面検索（「最全機能」の発見可能性）

ターミナルのボトルネックは決してコマンドの少なさではなく、**見つけられないこと**だった——CLI にはトップレベルコマンドが 64 個、第二階層を含む入口が 135 本ある。三つの入口がこれを解決する：

```bash
python scripts/nf.py shell --map                 # 能力マップ：能力ファミリ別に区画し、全コマンドを網羅
python scripts/nf.py shell --map 治理            # あるファミリだけを見る（コマンド断片での絞り込みも可）
python scripts/nf.py shell --commands            # 到達可能な全コマンドを列挙（トップレベル + 第二階層）
python scripts/nf.py shell --commands asset      # 部分文字列で絞り込み
python scripts/nf.py shell --search 装配         # キーワード検索（外れると exit 2、スクリプト化可）
python scripts/nf.py shell --verify              # ターミナルセルフチェック（索引 / キュレーション / メニューの三面、終了コードが結論）
python scripts/nf.py shell --verify --deep       # 生体版：読み取り専用コマンドを 1 本実際に走らせる + 落とし先の書き込み可否 + 環境事実
python scripts/nf.py shell --verify --json       # 機械面（純 JSON：ok / issues / stats）
python scripts/nf.py shell --complete "/ma"      # スラッシュコマンド補完 → /map、/menu…
python scripts/nf.py shell --complete "nf layers --"   # フラグ補完 → --json / --verify / --write
python scripts/nf.py shell --history <文件>      # セッション横断履歴（既定は <NF_HOME>/shell_history）
```

セッション内の等価な形は `/map [族]`、`/commands [过滤]`、`/find <词>`。三層が「最全」を主張でなく保証する：

① **索引は CLI の argparse 面から派生する**（ターミナルは第二のコマンド表を持たない）；② **能力マップは各コマンドをちょうど一つのファミリに割り当てる**（`start / forge / shelf / verify / library / govern / integrate / meta`）、「未キュレーション」なら報告する；③ 判定は**単源**——`nf shell --verify`（人が走らせる）と verify check39（ゲートが走らせる）は同じ `terminal.self_check` を呼ぶので、「ターミナルが問題なしと言う」と「ゲートが問題なしと言う」は常に同じ意味になる。

## 生体セルフチェックと機械面

### 一流 CLI ベースライン（項目ごとに検証可能、形容詞ではない）

```bash
python scripts/nf.py shell --baseline          # 根拠コマンドを行ごとに走らせて判定を出す（17 項目）
python scripts/nf.py shell --baseline --json   # 機械面（純 JSON：ok / stats / rows）
```

ベースラインの真源は `desktop/src/core/terminal.py` の `TERMINAL_BASELINE`：各行 = 一つの能力 + **一本の根拠コマンド**（+ 出現すべき / 出現してはならない断片 + 期待終了コード、必要なら + stdin 入力 + **ディスクに落ちることを期待するファイル**）。現在 **20 行**が覆う（下表は主題ごとに併合——4 本の書き込みゲート行は 1 項目に合成、行ごとの一覧は `terminal.py`）：コマンド面到達性 / キーワード検索 / 能力マップ / タイポ候補 / **書き込みゲート（拒否されるべき）** / **再帰常駐の遮断（拒否されるべき）** / 補完 / 長さ制限の通知 / 非 TTY 無色 / スクリプト面 / **履歴リプレイ** / **履歴ディスク書き込み** / **セッション永続化** / **メニュー↔ファミリ相互標識** / フォーム dry-run / 純 JSON 機械面 / 生体セルフチェック。

四つの規律：① 根拠行は**リポジトリを読むだけ**（`--write` / `--apply` / `--yes` などのフラグが付くとベースライン自身が違反と判定する）；② 「拒否されるべき」を宣言できる（`expect_exit: 2` + 実行拒否の理由）、これで安全面もベースラインに入る；③ 対話モードの根拠（履歴/セッション）は `{TMP}` プレースホルダを**システム一時ディレクトリ**配下の固定ディレクトリ `<临时目录>/nf_baseline` に展開し（リポジトリ外；固定名にするのは、`mkdtemp` が本環境では削除できず溜まるのを避けるため）、「ディスクに落ちることを期待するファイル」で状態が**本当に書かれた**ことをアサートする；④ verify check39 は同じ表を 1 行ずつアサートする——**「一流 CLI 対標」の完成度は項目ごとに検証できる**、見た目に頼らない。

- **`--verify --deep`（生体版）**：静的面（索引 / キュレーション / メニュー）の上に**本機環境と実行可能性**をさらに検める——① 読み取り専用コマンドを 1 本実際に走らせ（`nf layers --verify`）終了コードを照合する；② `nf <cmd> --help` を**1 本ずつ**走らせ（現在 64 本、読み取り専用、約 11 秒）終了コードを照合する——「最全機能」はこれで「索引で見つかる」から「コマンドが本当に通る」へ格上げされる；③ 履歴/セッションの落とし先の**書き込み可否**を探る（祖先ディレクトリをたどって判断、**プローブファイルは落とさない**）；④ TTY / readline / ページャの現状を正直に報告する。すべての結論は静的面と同じ口径（`terminal.deep_check` が `self_check` を呼ぶ）、終了コードが結論。
- **機械面（`--json`）**：`--commands --json`（コマンドごと + 要約 + フラグ）、`--map --json`（ファミリ区画）、`--form --json`（フォーム真源）/ `--form <id> --json`（アセンブリ計画 argv）、`--verify [--deep] --json`（ok / issues / stats）。**出力は純 JSON でなければならない**——生体出力は stdout に混ざらずフィールドに取り込まれ、check39 がその点を直接アサートする。

- **面判別キー（全コマンド口径 · 2026-10-01 収口）**：`--json` を宣言する面では、成功出力は必ず**オブジェクト**で、トップレベルに面判別キー `kind` を持つ（プロトコル件の面は `schema` を使う）；失敗は必ず `{"ok": false, "error": … , "exit": N}`。従来は新旧二世代のエンベロープが併存していた（引数なしで走れる `--json` 面 64 本を実走：キーあり 17 / なし 47、うち 7 本は裸の配列——成功は配列、失敗はオブジェクトを返すので消費側は**区別できない**）。本ラウンドで統一。**唯一の免除は `nf interop`**：これが輸出するのはサードパーティ標準文書（OpenAPI / AsyncAPI / SPDX / CycloneDX / in-toto / VC / C2PA / CID）であり、NF 私設キーを**付けてはならない**（付けると公式 meta-schema に越界と判定される、AUD-0010 で実測）、代わりに仕様自身のバージョンキーで自証する。判定：`desktop/tests/test_cli_json_face.py`（静的辞書面 + 動的実走 + 免除面の逐一指名）。

- **成功面は本機の絶対パスを吐き戻してはならない（2026-10-01 収口）**：同じ規律は以前、失敗メッセージ（`_no_machine_paths`）、入庫ファイル（`conformance_report._c_public_surface`）と `test_leak_surface` にしか書かれていなかった；実測では `nf doctor --json` / `nf toolface --json` / `nf daemon status --json` の三つの**成功面**が `C:\\Users\\<用户名>\\…` をそのまま書き出していた。現在は**リポジトリ相対**（doctor 明細、toolface の `source`）または**可搬な書き方**（daemon の `root` / `state_file` → `~/…`、`_portable_path` 参照）に変更。判定は `test_cli_json_face` に併合（機械面 + 人読面をそれぞれ本機パス形状で走査）。

## 単一の真値源 · 多ビュー（投影面）

ターミナル面には**真値が一つ**しかない：`desktop/src/core/terminal.py` のキュレーション表（`ZONES` 能力ゾーン + 動作目録 / `FAMILIES` 能力ファミリ / `FORMS` 書き込みフォーム / 書き込みゲート三表 / `BLOCKED_IN_SHELL`）、および `scripts/nf.py` の argparse 面（コマンドの**存在性**）。それ以外はすべてその**投影**である：

| ビュー | 何を提示するか | 入口 |
|---|---|---|
| 行モードターミナル | メニュー例 / 能力ファミリマップ / 書き込みフォームの項目ごとの問い合わせ | `nf shell`（本ファイル上文の各節） |
| 全画面 TUI | 動作目録（**書き込みフォーム区**を含む：13 表それぞれが Enter で実行できる動作） | `python tui/nf.py` |
| 機械面 | 面全体のスナップショット（JSON） | `nf shell --surface --json` |
| 生成件 | 全画面ビューのオフライン入力（core 依存ゼロ） | `tui/_surface.py` |

```bash
python scripts/nf.py shell --surface            # 人読面：区ごとに動作とゲート件数を列挙
python scripts/nf.py shell --surface --json     # 機械面：kind=nf-terminal-surface
python scripts/nf.py shell --surface-write      # tui/_surface.py を再生成（真源変更後は必ず走らせる）
```

三つの規律：

1. **ビューに第二の表を残してはならない**。全画面 TUI は単一ファイル exe に凍結され core を import できない。そのため以前はコマンドホワイトリスト / ゲート表 / 動作目録を手写ししていた——手写しのゲート表は「コマンド + フラグで書き込み」のペア表（`terminal.CONFIRM_FLAG_PAIRS`）を漏らし、`nf interop --all` のような書き込み面が全画面ビューで**確認なしに実行できて**いた。現在 TUI は `import _surface`（生成件）だけを行い、口径は真源が唯一保持する；ビューは**明示的に**さらに厳格化してよい（例：TUI は `daemon` ファミリ全体を実行拒否に並べ、理由は `TUI_EXTRA_LONG_RUNNING` に書く——ビュー方針であって分岐ではない）。

2. **投影は照合可能でなければならない**。`tui/_surface.py` は**生成件**（件内の冒頭に真源と再生命令を明記）。真源を変えて再生成しない ⇒ `nf shell --verify` と verify check39 の両方が赤になる：投影を再計算し、在场する件と**バイト単位**で照合し、最初の不一致行と再生成コマンドを報告する。

3. **ビューの口径はより厳しくするのみで、より緩くはできない**。check39 が項目ごとに照合する：全画面ビューの書き込みフラグ / 書き込み動詞 / コマンド + フラグのペアは真源の三表を**覆わ**なければならない；コマンドホワイトリストは argparse 面と一致しなければならない；動作の `argv[0]` は実在のコマンドでなければならない；能力ゾーン数は真源と一致しなければならない。ビュー側の書き込み面も同じくゲートに縛られる：フォームから実体化された動作は `write` と判定されなければならず（単体テストで 1 行ずつ列挙）、空の任意パラメータはそのフラグごと捨てる（`terminal.build_argv` と同じ口径、宙に浮いた `--reason` を残さないため）。

判定の落とし所：`verify.sh` check39（投影バイト単位 + ビューが真源より弱くないこと）、`desktop/tests/test_terminal.py`（`TerminalSurfaceTest`）、`desktop/tests/test_nf_tui.py`（`SurfaceSingleSourceTest`）、`python tui/nf.py --selftest`（「ゲート口径（単源）」「投影同源」の 2 行）。

## 書き込みフォームとセッション状態（リポジトリを変える動作は人が安全に駆動する）

`nf` の書き込みコマンドはパラメータを揃えたうえで `--yes` が要り、人には負担である。ターミナルはこれを**項目ごとの問い合わせ**に分解する：`/form <id>` で開始し、1 回に 1 項目尋ね（任意項目は**空行でスキップ**）、埋め終えたら**組み立て済みのコマンド**を印字してから `yes/no` を問い、確認後にのみ実行する——しかも最終的には同じ**書き込みゲート**を通る（ターミナルはこれを迂回しない）。現在 **13 表**がよく使う書き込み点を覆う：`deprecate-module` / `restore-module` / `types-write` / `stats-write` / `asset-add` / `register-apply` / `rename-apply` / `receipts-write` / `preset-save` / `library-deprecate` / `library-restore` / `pipeline-new` / `approve-subject`。**残りの書き込み面は `terminal.FORM_EXEMPT` に 1 行ずつ登録する**（なぜ表を作らないかを明記）。判定は「ゲート表の各書き込み面は表を持つか理由を持つかのいずれか」を保証する——新しい書き込み面がゲートに入ったのに誰も表を用意し忘れれば赤になる。

この 13 表は**同時に全画面ビューの動作**でもある：`ZONES` の第 8 区（`id=forms`）は `forms: True` と標識され、動作は `terminal.zone_action_dicts()` が `FORMS` から投影する——ゆえに「フォームの真源は一つだけ」（表を変えれば両ビューが変わり、二度目の登録は存在しない）。フォーム手順で `kind: "path"` を持つパラメータは全画面ビューで**パスパラメータ**になる：リポジトリ包含性の判定を通ってからでないと argv に組み込まれない。

非対話でも使える（dry-run 優先）：

```bash
python scripts/nf.py shell --form                                # 全フォームを列挙
python scripts/nf.py shell --form stats-write                    # 組み立て + 印字のみ（dry-run）
python scripts/nf.py shell --form deprecate-module --answer file=community/x/M1.md --answer reason=重复
python scripts/nf.py shell --form stats-write --yes              # 明示的に放行したときだけ実際に実行
```

- **パラメータ真源**：フォームテンプレート内の `{key}` は step が埋める；テンプレートは**実在の CLI 動詞**しか指せない（check39 がアサート）、空値はそのフラグごと捨てる（宙に浮いた `--reason` を残さない）。**ブールフラグ**は「単一プレースホルダ」で表す：`{key}` を単独のマスに置き、`--force` を入れれば付き、空なら捨てる（`preset-save` 参照）。
- **二次確認**：対話モードでは `yes/no`；非対話モードでは明示的な `--yes` が必須（既定は dry-run のみ）。
- **セッション状態**：`--session <文件>` がビュー設定と前回の区画を永続化する（`/set` の直後にディスクへ落ちる）。ガード：パスは**絶対**でなければならず、**リポジトリ内に落ちてはならない**——リポジトリに状態件を残すと `git add -A` に呑まれる（2026-09-26 に tmp ファイル事故を一度実測）。

## 効率（「速い」も判定にする）

ターミナルの二種類の効率にはそれぞれ判定がある：

**① プロセス内オーバーヘッド（機構コスト）**

- **コマンド面は一度しか構築しない**：argparse 面の構築は実測 **96–118 ms/回**、かつては 1 回のターミナルコマンドで 3 回以上構築していた（索引 + コマンド木 + 実際の解析）、`--verify --deep` の全コマンド走査に至っては **64 回**。現在 `_build_parser()` / `_collect_cli_tree()` / `_shell_command_index()` はすべてプロセス内キャッシュ。
- **`--version` 短絡**：最も呼ばれる探査コマンドはもうコマンド面を構築しない（出力は argparse の version アクションと逐語一致）。
- **幅クエリのキャッシュ**：`char_width()` は `lru_cache(4096)` を持つ——一覧描画は 1 文字ごとに幅を問うホットパス。
- **抽象ラダー真源面の展開（v13）**：`nf layers --verify` は唯一まだ ~1 s の固定コストを持つ読み取り専用コマンドで、コストはほぼ glob 展開にある——`_rule_issues` の L1/L2/L3 は同じ 43 個の pattern を繰り返し展開し（約 10.5k 回の `stat`）、L6 はさらに core 全体を `ast.parse` する。現在：走査ごとに pattern 単位でキャッシュし、各部分木は `os.walk` を一度だけ + glob→正規表現マッチ（文字クラスなど固有の意味論は参照実装に退避）、L6 はテキストで事前選別してから AST を解析する。ファストパスは参照実装と**pattern ごとに等価**（真源の 43 pattern + 文字クラス / `?` / `**` / 固定件 / 空部分木の 5 形態、不一致 0）、四階面の規模は不変（契約 52 / アセット 2218 / エンジン 256 / 出口 26）。
- **コア走査の重複排除（v14）**：ターミナル以外の読み取り専用コマンドも同じ規律で締めた——`nf conformance` はかつて十八項契約を**二度走らせ**（まず照合、次に印字）、現在は一度だけ；`nf doctor` では 248 件のモジュール文書の機械契約ブロックが **496 回**解析されていた（健診の 74%）、テキスト**そのもの**をキーに解析をキャッシュする方式に変更（テキストが変わればキーが変わる、陳腐化リスクなし）；パイプライン dry-run の `sweep()` は 228 本のパイプラインごとに全リポジトリのモジュール索引を構築していた（≈5.6 万回の読盤）、一度だけ構築する方式に変更；純度スキャンは同じ木を 4 回 walk していたが、**一度の parse + 一度の walk** で四種類の事実を揃える方式に変更；広度証明は組合せごとにキャッシュキーを取る際 `Path.resolve()`（Windows のシステムコール）を 1 回通していたが、`os.path.abspath` に変更——**6888 組合せで 3.8 s 節約**。等価性は参照実装との項目ごとの照合で守る（純度 issues/stats 全等、広度の組合せ数と合法性全等）。
- **同文の再計算を内容キーキャッシュに変更（v15）**：アセット参照度普查（1499 キー × 3.5 MB をキーごとに正確に計数 ≈ 2.9 s）は**コーパスとキー集合の sha256** でキャッシュする——キーはパスでなく内容を取り、内容が変わればキーが変わるので陳腐化リスクがない；同一プロセス内 2 回目の普查は 2.94 s → 0.88 s。他に純粋な重複 IO を 2 か所修正：`conformance_scan` は**コミュニティパッケージごと**のループで registry.json を再読していた（112 回）、`asset_density._keys_of` は呼び出し側が読んだばかりの正文をもう一度読んでいた。**二つの「加速」は実測で否決**：`bytes.count` はより遅く（UTF-8 希釈）、単一パスの alternation はキーが同一位置で重なると過少計数する（「ゼロ参照キー」を偽のゼロにする）——正確な意味論を優先する。
- **統一 YAML ローダを libyaml に変更（v16）**：帰因の結果、残った YAML コストは**重複解析ではなくパーサが遅いこと**だった（`schema_lint` の 473 回解析は重複ゼロ、`concept_graph` の 102 件の概念図は真の解析）。`CSafeLoader` は `SafeLoader` より **7.8× 速い**と実測；共有入口 `conformance_scan.load_yaml()` を新設（libyaml 優先、なければ純 Python に退避）、4 か所のホット解析点を統合。等価性は**ブロックごとに実証**：本リポジトリの 1395 個の YAML テキストブロック（584 ファイル）で両ローダの結果と例外挙動が**全等**（回帰アサーションとして固定済み）。初版が `yaml.load(...)` を使ったところ自家の純度判定 R6 に CWE-502 の危険 sink と判定された——安全ローダを直接インスタンス化する方式に変更（`yaml.safe_load` と同じ意味論）、禁止面を呼び戻さない。

**② レイテンシ予算（ベースライン行が `max_ms` を自前で持つ）**

`nf shell --baseline` は現在**根拠行ごとに計時**し、人読出力と並べて出す（`✔ … 1.7 ms nf shell --commands …`）：軽い行の既定予算は **300 ms**（実測 ~1–2 ms、100× の余裕、それでも「パーサキャッシュが失効 → ~300 ms 級に膨らむ」といった回帰は止められる）、`--verify --deep` 行には単独で **6000 ms** を与える（2026-09-29 に**実測で再標定**：この行の主コストは**全リポジトリの抽象ラダー走査** `nf layers --verify`——アイドル時 ~0.5–1.7 s、本機高負荷時 2.4–3.7 s；旧標定の「プロセス内 ~320 ms、6× の余裕」という前提はもはや成立せず、2000 ms では 1.15× の余裕しか残らず、同じ木で実測が一度緑一度赤になった。6000 ms ≈ アイドル余裕 3.5× で、なお「全コマンド走査が ~11 s に戻る」といった桁レベルの回帰は止められる）、さらに**予算超過の行はもう 2 回測って最小サンプルを取る**（min of N は本リポジトリ一貫の性能口径——予算が測るのは機構コストであり、その時のこのマシンの機嫌ではない）。予算超過ならその行は不合格 → check39 赤 → 上げられない。

**③ 打鍵を減らす（ユーザ効率）**

- **一意プレフィックス補完**：`scor` と入力すると自動で `score` に補完する（**候補がちょうど一つ**のときだけ働き、明示的に标注する；曖昧なときはタイポ候補に回し、勝手に推測して実行しない——例えば `stat` は stats と state-front の両候補に当たる）。
- 既存の補完（Tab / `/complete`）、履歴リプレイ（`!!` / `!n` / `!前缀`）、能力マップと検索を合わせれば、常用動作の打鍵数は一桁に収まる。

**④ 読み取り形状（「重複して読まない」を判定にする）**

ウォールクロックの断言は CI / 並発機では揺れるが、「同じ件が 1 回の走査で何回読まれるか」は**決定的**である——そこで本ラウンドで直した欠陥クラスを読取り回数の判定として固定する：`library.search` は 300 件所蔵で**1 件あたり ≤ 2 回、総読取り回数は件数に対し線形**（さらに変異サンプルが、この限界が旧実装の O(n²) 形状を捕まえられることを示す）；1 回の縦深走査は**1 件あたり最大 ≤ 14 回**（実測平均 3.5、単件最大 9）。同種の回帰（各条目/各結果ごとに全量読み取りを再実行する）は「ただ遅くなる」のではなく即座に赤になる。

## 出力体験（カラム幅 / 長さ制限 / 着色 / ページング）

- **カラム幅の整列**：CJK と emoji は**表示幅 2** として計算する（`display_width` / `pad_to` / `clip`）、二列一覧は中国語ターミナルで列がずれない；幅は `--width`、なければ環境変数 `COLUMNS`、なければ 100。
- **長さ制限と通知**：`--limit N`（0 = 全部）は長い一覧に効き、切り詰め時は「… あと M 件（`--limit 0` で全部、または絞り込み語を足して収束）」と明示し、黙って切り詰めない。
- **着色は控えめに**：`--color=auto|always|never`（既定 auto）。auto は**真の TTY かつ `NO_COLOR` 未設定**のときだけ着色する；`NO_COLOR` は auto を一票否決し、`always` は明示的な要求でその影響を受けない。セッション内では `/set color=never` でいつでも切れる。
- **決定性契約（ハード）**：非 TTY（パイプ / CI / テスト / `--exec` / `--file`）は一律**無色・無ページング・バイト単位で再現可能**——verify check39 が既定出力に制御文字が含まれないことを直接アサートする。
- **ページングは任意**：`--pager=auto` のときだけ、真の TTY で `less` / `more` が在场する場合に長い出力を引き受ける；既定は `never`（リダイレクト可・diff 可を保証）。

## 補完と履歴（依存ゼロ口径）

一流 CLI の体感は主に二つにある：**半分打てば補完できる**、**前の一巡へ遡れる**。NF は両方を**判定**にし、プラットフォーム機能にはしない：

- **補完**：`complete()` は純関数（どのプラットフォームでも使える：`/complete <前缀>`、行末 `Tab`、`nf shell --complete`）、候補はコマンド / 第二階層サブコマンド / フラグ / スラッシュコマンド / 能力ファミリを覆う；POSIX では `readline` が使えれば Tab を自動で引き受ける（`install_readline`）、Windows で同モジュールがなければ候補一覧に退避する——`nf shell --verify` は現在どちらの経路かを正直に報告する。
- **履歴**：**対話モード**のみが `<NF_HOME>/shell_history` に書く（`--history <文件>` でパス変更、`--no-history` で無効化）；`quit` と Tab 行は履歴に入らない；`--exec` / `--file` は**一切書かない**——スクリプト面の決定性はハード契約（単体テストが `run_lines` に履歴フックがないことを直接アサート）。

セッション内では三種のコマンドを**実行しない**（ターミナルのハングを避ける）：`serve`（常駐 MCP サービス）、`lsp`（常駐 stdio サービス、エディタが Content-Length フレームを送るのを待つ——`serve` と同型、2026-10-01 に补齐）と `shell`（再帰セッション、`nf terminal` はその別名で同じく遮断）——ターミナルは案内だけを出し、別のターミナルを開くか IDE に起動させる。

## 書き込みゲート

**真源 = `desktop/src/core/terminal.py` の三表**（`CONFIRM_FLAGS` / `CONFIRM_VERBS` / `CONFIRM_FLAG_PAIRS`）；本ページは口径と**抜粋**一覧のみを書き、判定は本ページに現れる各項目が本当に表にあることを照合する（ドキュメントの漂流防止）。以下のいずれかの形態に当たれば書き込み / 不可逆面とみなし、既定で実行を拒否する（終了コード 2 + 修復案内）：

- 標識フラグ：`--write` `--apply` `--register` `--force` `--out` `--dest` `--build`、および**名前に `--write` がないのに同じく書き込む**もの：`--write-baseline`（`nf score` が回帰ベースラインを再署名；`nf asset baseline` の再署名は `--write` を使う）、`--fix`（`nf lint` の機械修復がソース件をその場で書き換える）、`--harvest`（`nf module types` がイベントペイロードレジストリを書く）、`--write-advisory`（`nf pipeline dryrun` がパイプライン advisory 台帳を書く）、`--certify`（`nf combine plan` が組合せ証明書を書く）、`--save`（`nf assemble` が**あなたが命名する**アーカイブファイルを書き、リポジトリ相対パスを渡せる ⇒ `--out` と同類）、`--surface-write`（`nf shell` **自身**の生成器フラグ：ターミナル面の真源を `tui/_surface.py` に投影する；CLI トップレベルからのみ到達可能——`shell` はセッション内で実行拒否される）
- 動詞（**フラグを一切付けなくてもリポジトリ件を直接変える**）：`register` / `import` / `rename` / `release` / `approve`（`protocol/approvals/*.json` を落とす）/ `asset add|rm|deprecate|restore` / `module deprecate|restore|signature` / `pipeline new` / `decisions reindex` / `patterns reindex` / `knowledge transform`（`protocol/transform_log.json` を書く）/ `library reindex|deprecate|restore|supersede|attest`

- コマンド + フラグのペア：`interop --all`（`results/interop/*` を落とす；同名の `interop --check` は読み取り専用で遮断しない——`pipeline dryrun --all` も同じ）；`--trace` / `--session` は **`nf assemble` 上でのみ書き込みとみなす**（あなたが命名するファイルを書く）——`nf knowledge frequency --trace` は**読み**であり、`nf shell --session` には別途「絶対パスでなければならずリポジトリ内に落ちてはならない」というハードゲートがあるので、どちらも遮断しない

放行の方法は二つだけ：対話セッションでその場で `yes` と答える（その回だけ放行する）、または呼び出し側が明示的に `--yes` を渡す。

**ゲートが守る面（口径）**：守るのは**テキスト駆動**の面だけ——対話入力、`nf shell --exec`、`nf shell --file`（この三つはいずれも**貼り付け/注入**されたテキストを運びうるし、機械が人の代わりに「この行を走らせるべきか」を判断はしない）。**明示的 argv** の面にはこのゲートを設けない：`nf <cmd> …` の直接実行と `nf daemon exec <argv>` は操作者自身が打ったコマンドと等価である（後者はドキュメントに「出力/終了コードは直接実行と一致」と明記されている）。実測対照：`nf shell --exec "nf stats --write"` → exit 2（拒否）、`--yes` を足せば放行；`nf daemon exec stats --write` → そのまま走る。

## 非対話モード（CI / スクリプト / 回帰）

## 実行層常駐（`nf daemon`）——ミリ秒級応答

`nf <命令>` は毎回インタプリタを起動する。本機実測（2026-09-29、min of N）：**裸のインタプリタ 47 ms**、`nf --version` **215 ms**——固定コスト ≈ インタプリタ起動 + import（~10 ms）+ **argparse コマンド面の構築（実測 117 ms、65 サブコマンド）**。`nf daemon` は実行を常駐プロセスへ移し、クライアントはソケット往復を 1 回だけ行う（熱いプロセス内で `--version` **1.5 ms**；bash 内蔵の `$EPOCHREALTIME` で計量、fork ゼロ、`date` の偏りなし）。

| 経路 | `--version` | `stats --check` | `doctor` |
|---|---|---|---|
| python 直接実行（元の経路、コマンドごとに 1 回インタプリタ） | 215 ms | 288 ms | 634 ms |
| `scripts/nf` ランチャー（**デーモンなし**：python 直接実行に退避） | 296 ms | 365 ms | 713 ms |
| `scripts/nf` ランチャー（デーモン経由） | 48 ms | 48 ms | 48 ms |
| **bash 関数（子プロセスゼロ、デーモン経由）** | **1.5 ms** | **1.6 ms** | **1.6 ms** |

ランチャー自身に今残るのは **bash 起動フロア（本機 ~39 ms）+ ソケット往復 1 回**だけ。修正前は「同じコマンドの python 直接実行」より **164 ms 遅かった**——三つの固定コストはいずれも**コマンドごと**に計上されていた：外部 `dirname` + サブシェル ≈58 ms、コマンド置換 1 回（Store スタブ経路の判定）≈30 ms、「本当にインタプリタを起動するか」の終判 ≈60 ms（Microsoft Store の別名スタブに実際に当たると ~300 ms）。三つをそれぞれパラメータ展開、プラットフォーム別の択一（Windows は `python` を先に要求）、終判を「インタプリタ名 + プラットフォーム」で**キャッシュ**する方式に変えた結果：ランチャーはデーモン経由 **175 ms → 48 ms**、デーモンなし **428 ms → 296 ms**。判定は**インタプリタ起動回数**（PATH に shim を掛ける：先に 1 回記録してから真のインタプリタへ転送、マシンの速さと無関係）——ファストパス命中は **0 回**、退避は**定常状態でちょうど 1 回**（修正前はコマンドごとに 2 回）、`python3` がスタブのときは動く方に切り替える必要がある（`test_launcher.InterpreterLaunchBudgetTest`）。

> **2026-10-02 同口径の再測（min of 5、同一手法）**：bash フロア **40.8 ms**、`scripts/nf --version` デーモン経由 **71.9 ms**（インタプリタを 1 回も起動しない）、デーモンなし **260.9 ms**（ちょうど 1 回）、`python scripts/nf.py --version` **189.3 ms**。つまり上表の「デーモン経由 48 ms」の内訳は今や **フロア 41 ms + ソケット往復 ≈31 ms**（当時の往復は ≈9 ms）であり、合成式（フロア + 往復 1 回）は変わらない；「デーモンなし 296 ms」は今日の 261 ms と同じ桁。
> 口径の注意：本節の数値は**日付付きの実測記録**であり、約束ではない——**機構面**（ファストパスが何回インタプリタを起動するか、退避が定常で何回か）は `test_launcher.InterpreterLaunchBudgetTest` が決定的に守り、**ウォールクロック数値**はマシンと負荷で漂う。再測時は「同一ラウンドでウォールクロック + 起動回数を同時に測る」手法を踏襲せよ（初版はウォールクロックだけを測り、起動回数と同ラウンドで比べなかったため、デーモンなし経路をファストパスと同速と読み違えた）。

### 再計算しない：ディレクトリ監視 + レスポンスキャッシュ（`nf daemon start --watch`、任意）

「mtime/size で変わったか否かを推測する」道は明示的に否決された（フィンガープリントが不変 ≠ ファイルが不変；Windows のタイムスタンプ粒度 ~15.6 ms）。本波は**「変わったように見えるか」を問わず、「変わったか」だけを問う**道に切り替える：デーモンはディレクトリ監視を装着し（Windows：`ReadDirectoryChangesW`、部分木を再帰）、**木の世代**を維持する；読み取り専用コマンドの**応答全体**を `(argv, cwd)` でキャッシュし、**世代が変わっていないときだけ再利用**する。

| 経路 | `nf score` |
|---|---|
| コールドスタート直接実行 | 7.7 s |
| デーモン定常（毎回本当に再計算） | ~2.2 s |
| **デーモン + `--watch`（木が不変 → 応答全体を再利用）** | **~0.18 s**（差額は `bash scripts/nf` のプロセス起動） |
| 同上、子プロセスゼロのクライアント併用 | **5 ms/回**（3 ラウンド ×20 サンプル；プロトコル往復、子プロセスなし） |

実測（本機）：同じ木で `nf score` を 2 回連続 → **6816 ms / 176 ms**；リポジトリで一時ファイルを増減した後 → **2087 ms（再計算）**、もう一度走らせると → **177 ms**。

規律（fail-closed、いずれも判定あり）：

- **「変更通知を受け取った」だけを「変わった」とみなす**：監視不可用 / ハンドル失効 / スレッド例外 → キャッシュを全体停止（命中せず、旧条目もまとめて無効化）、挙動は通常のデーモンと完全に同一；バッファオーバーフローは正直に `overflowed` と報告し、世代を跳ばせる（全廃の方が誤答よりまし）。
- **デーモン自身が「非准入」コマンドを実行した ⇒ 直ちにバッチ全体を無効化**、**監視スレッドが非同期に気づくのを待たない**：無効化は本来監視の数ミリ秒の窓に頼っていたが、スクリプト内で `nf conformance --write; nf score` のような連続実行をするとその窓に落ち、書き込み前の古い応答を食べる可能性があった（タイミングに頼らず、決定的な判定が守る）。**残留窓は正直に記録**：外部プロセスがリポジトリを変え、要求が監視の気づく数ミリ秒前に届くと、なお古い応答に当たりうる——これは通知制キャッシュの固有の窓；デーモン側の書き込みは上の規則で**決定的**な無効化になった。
- **二つの fail-closed ゲート（ハンドルを開けた ≠ 通知が届く）**：① **ボリューム種別**——本機の固定ディスクでのみ有効化（ネットワークドライブ SMB/UNC の通知意味論は信頼できず、イベントを静かに取りこぼす → 世代が永遠に進まず＝永久に旧結果を再生する）；② **機構セルフチェック**——起動時に**一時ディレクトリ**で「作成 / 変更 / 削除」を実際に走らせ、三種の通知がすべて届いて初めて使用可とする。どちらかが通らなければ「監視不可用」と判定し、キャッシュを全体停止。コストは実測で ~70–90 ms のみ（`nf daemon start --watch` 565 → ~650 ms、一過性）。
- **`.git/` 下の変更はレスポンスキャッシュを無効化しない**：日常の `git status/add/commit` は `.git/` に書く。従来通り無効化すると、git コマンドを走らせるたびに次の `nf score` が ~2.2 s の再計算に戻ってしまう（実測：修正前は `.git` プローブ後で平均 **151 ms**、修正後は **10 ms**）。安全の前提は**判定に裏打ちされた事実**——1 回の `evaluate` の全オープンと試行オープンを追跡し、`.git/` を含むパスは **0 件**でなければならない（実測でリポジトリ内 2560 件、`.git` 下 0 件）、かつキャッシュ対象の読み取り専用コマンドはいずれも git を呼ばない。混在バッチ、パスが解析できない、バッファオーバーフローは**すべて従来通り汚れる**（「このバッチが全部忽略面に落ちる」場合のみ無視する）。
- **准入リストは argv 接頭辞で**（トップレベルコマンド名ではない）：**純粋に読み取り専用で、同じ木に対してバイト単位で再現可能**な形態だけがキャッシュ可能——`--version` / `score` / `conformance` / `layers` / `stats` / `doctor` / `interop` / `toolface` / `assertions` / `cognition`、および `patterns ls|show|for|verify` / `module ls|status|verify` / `decisions verify|show`。`--write` のような書き込みスイッチを持つものは一律迂回する。
  「接頭辞で」は必須である：`module` / `decisions` / `patterns` といったトップレベルコマンドは**読みと書きのサブコマンドを同時に持つ**（`module deprecate`、`decisions reindex`、`patterns reindex`）。トップレベル名だけで放行すると書き形態まで一緒に入ってしまう。二つの准入判定はどちらも実行可能：① 同じ木で 2 回連続実行し、終了コード / stdout / stderr がバイト単位で同一；② 各々を走らせる前後で `git status` が不変（候補 12 本の実測はすべて純粋かつ再現可能だった）。
- **本波は Windows の監視のみ実装**：他プラットフォームでは `watch.available()` が偽で、デーモンは自動的に降級する——走らせていないプラットフォームのコードは書かない。
- **自動起動（既定オン · 非ブロッキング；`NF_AUTOSTART=0` で無効化）**：デーモンがいないとき、ランチャーは `--watch` 付きのデーモンを**バックグラウンドへ放り込んで**起動し、**本コマンドは通常通り python 直接実行で走り、待たない**（`daemon` / `shell` / `terminal` / `serve` / `lsp` は元々デーモンを通らず、発火しない）。**なぜ既定オンか**：デーモン起動には ~0.65 s かかるが、バックグラウンド起動は**本コマンドの時間を食わない**（1 本目は fork 1 回 ≈10 ms が増えるだけ）、そして**2 本目以降はコマンドがデーモンのファストパスに落ちる**。実測（本機、各 7 連発の中央値；**数値はマシンで変わる、桁の参照にすぎない**）：`python scripts/nf.py stats --json` **≈223 ms**（コマンドごとにインタプリタをコールド起動）· `bash scripts/nf stats --json` **≈123 ms** · `scripts/nf.cmd stats --json` **≈194 ms**（2026-10-01 以降 `scripts/nf_client.py` 経由でファストパス；**以前 ≈391 ms**）。`.cmd` の階層は依然**POSIX ランチャーより遅い**（cmd.exe の外殻が一枚多く、自身のクライアント `python -S scripts/nf_client.py` ≈155 ms よりさらに ≈40 ms 多い）——ミリ秒級の階層は POSIX ランチャー `scripts/nf` + `eval "$(nf daemon shell-init bash)"` である。既定経路はゆえに「agent の稠密な反復呼び出し」にはミリ秒級；一度きりのコマンドしか走らせずデーモンを常駐させたくないなら、`NF_AUTOSTART=0` で切ればよい（`nf daemon exec` は同類の意味論：あちらは既定で起動し、`--no-start` で拒否できる）。

### 再読しない：常駐コーパス + ディレクトリ索引（監視変更で**正確**に失効）

レスポンスキャッシュは「木が不変」の階層しか扱わない；**一つのファイルを変えた後**はどうか？実測（本機、min of N）：編集直後に `nf score` を走らせると、デーモン内の**1 本目**は **1.6–2.0 s** かかる——それらの共有コーパスキャッシュの作用域境界が「一度の呼び出し」だからで、次の要求はコーパス全体を**再列挙**（1484 ディレクトリ / ~2000 回の `scandir`）し**再読**（~2500 回の open）しなければならない。しかも実際に変わったのはしばしば 1 件だけである。

本波は**常駐層**を一段足す（`conformance_scan._RESIDENT`：正文 + ディレクトリ条目）。デーモンが**健全な監視**を伴うときだけ装着し、**監視根の下**の件だけを収録し、**監視が与えた確知パスのみ**で失効させる：正文は件ごとに削除、ディレクトリ条目は親ディレクトリごとに削除（増減はいずれも親ディレクトリの一覧を変える）。**言い切れないならバッチ全体を無効化**（バッファオーバーフロー / パスが解析できない / 世代だけ跳んでパスを渡さない）。

| シナリオ（デーモン熱走、編集直後の最初の `nf score`） | 常駐層オフ | 常駐層オン |
|---|---|---|
| `CHANGELOG.md` のような**どの入力面にもない**件を変える | 1591 ms | **872 ms** |
| `04_模块库/通用类/` に 1 件を置く（**入力面に落ちる**） | 1625 ms | **951 ms** |

（同機、各 3 ラウンドの中央値；スイッチは `NF_NO_RESIDENT=1`、いつでも旧挙動に戻して対照できる。）

なぜこれが**レスポンスキャッシュより何も多く信頼しない**のか：レスポンスキャッシュは元々同じ「世代が不変 ⇒ 木が不変」という判定に依っており、その判定はボリューム種別ゲート + 機構セルフチェック + 溢出報告が守っている。常駐層は同じ信頼をより多くのデータに使うだけで、**新しい失効経路を持たない**——監視が言い切れないときはバッチ全体を無効化し、レスポンスキャッシュ（旧応答を残すが世代は跳ぶ）より保守的である。判定（決定的、ウォールクロックを見ない）：変更面がパスを報告でき、知ったかぶりを拒否する（`DirWatcherTest`）、層は根の下の件だけを収録する、確知パスを与えられたら直ちに失効する、言い切れなければバッチ全体をゼロにする、デーモンが実際に装着し `_bump()` 後にゼロにする（`ResidentLayerTest` + `WatchDaemonIntegrationTest`）。

さらに下の層は**派生結果**：スキャナの結果はすべて「入力内容の純関数」なので、**入力面の内容フィンガープリント**でキャッシュする（プロセス内 + ディスクの二層；キーにはコード面と実行時も含む）。二つの規律が形を決める：

- **狭い面はどのプロセスでもキャッシュする**（アセット密度の二関数、台帳投影）——ウィットネスは数十ミリ秒で済む、価値がある。
- **広い面は常駐層が在位するときだけキャッシュする**（`schema_lint` / ラダー / 純度：宣言面がコーパス全体を覆う）——コールドプロセスでは広い面のフィンガープリントがコーパスを読み直すことになり（実測 ~1.0 s）、直接計算より高くつくので**計算しない方がまし**（`require_resident`）。

そして「ウィットネス」自体もほぼゼロまで押し下げられた：**件ごとの摘要が正文と一緒に常駐**し、監視変更で**件ごとに**失効する。実測では 8 個の入力面（3439 件の広い面を含む）のウィットネスコストが **228 → ~30 ms**、しかも**フィンガープリント値はビット単位で不変**（同一件同一 payload ⇒ 同一摘要）。エンドツーエンド（本機、3 ラウンド独立の中央値、各ラウンドでデーモンを新規起動）：

| 編集直後の最初の `nf score` | 修正前 | 修正後 |
|---|---|---|
| 無関係な変更（どの入力面にもない件を変える） | 1591 ms | **545 ms** |
| 関連する変更（入力面の件を変える、**唯一の新しい内容状態**、エンドツーエンド） | 1625 ms（Aho 以前は 4.6–6.3 s） | **≈1.25 s**（同一状態の再実行 ~52 ms） |
| 木が不変（応答全体を再利用） | — | **51 ms** |

**「新しい内容状態」という四文字は重要である**：同じ内容状態を 2 回目に走らせるとディスク上の条目に命中する（~50 ms）が、**本当の編集は毎回新しい状態**である。この区別をきちんと量って初めて真の元凶が見える——参照度普查はキーごとの `str.count` で 1499 キー × 3.5 MB のコーパスを数え、**5.2 GB の文字走査 = 3.11 s**、新しい状態ごとに毎回支払っていた。現在は **Aho–Corasick** に置き換えた（コーパスを一巡 + キー集合ごとに非重複の貪欲計数、`str.count` と**バイト単位で同意味論**）：真のコーパスで **2895 → 323 ms**（合計参照 31323 はキーごとに一致）、`usage_scan` 全体 ~3.1 s → **296 ms**、等価性は 400 例のランダム文字列 + 重複/入れ子/空キー境界 + 真のコーパス部分集合の三判定が守る。

さらに一歩（2026-09-29）：普查を**件ごとに計数してから合算**する方式にし、件ごとの結果を**ファイル内容**でキャッシュする——等価性は証明可能（asset id に改行が含まれない ⇒ 件を跨ぐマッチは存在しない）。ゆえに**1 回の本当の編集で再計算されるのは変わったその 1 件だけ**：`usage_scan` は件ごとキャッシュが熱いとき **296 → 28 ms**、エンドツーエンドの「本当の編集後の最初の重いコマンド」は **1.95 s → 0.35 s**（同一状態の再実行は依然 ~50 ms、コールドプロセスは ~1.87 s で不変）。

**口径の規律（三度踏んだ、ここに書き切る）**：何かを「新しい内容状態」と呼ぶなら、プローブは**一度きりの一意な正文**（タイムスタンプ + カウンタ）を書かなければならない。さもなければ 2 回目以降はディスク上の**同じ内容状態**の派生に命中し、量っているのは「同内容の再生」であって新しい状態ではない。この規律で再測：**一意な新状態 · デーモンの 1 本目 ≈ 1.25 s**、同一状態の再実行 ~52 ms、木が不変 ~50 ms、コールドプロセス ~1.9 s。

**共有読みは今や「一度の物理読みで二つの口径に仕える」**：下層は**生バイト**だけを読み常駐層に収める。テキストは `TextIOWrapper(BytesIO(raw), encoding="utf-8", newline=None)` で解く（`Path.read_text` の汎用改行意味論と**バイト単位で一致**、判定 `ResidentRawEquivalenceTest` が真のコーパスを件ごとに照合）。ゆえに「同じ件をテキストとしてもバイトとしても読む」（`ET.parse`、`_recompute_entry` のバイト照合など）は二度読まない——1 回の「新しい内容状態」の再計算で実際の読盤は **1047 回から 38 回**へ（異なり件 1039 → 33）。

縦深集約（`quality_depth_scan`、check32 ゲート面）は自ら**十数の子スキャナを 1 つずつ走らせる**ので、これにも内容キーキャッシュを接続した（入力面 = 各子スキャナ面の和集合）——残った勘定の最大の一箇所であり、接続後は**プロセス内 `evaluate` 476 → 43 ms**。同時に「表引き」自体も安くした：パスキー（`normcase(abspath())`）に記憶を持たせた（実測で 1 回の `evaluate` 内で 17628 回呼ばれ、単独で 71 ms を食っていた）。

**コード面（誰が本当に誰のコードに依存するか）も内容キーの一部**であり、コード面が一塊（119 件）だと「core ファイルをどれか 1 つ変える ⇒ すべての派生がキーを替える」を意味する。現在は**インポートクロージャ**で細分化する：各派生は「自分が静的に import した `core.*` モジュール」（推移閉包）だけをキーに入れる。三つの fail-closed：解析不能 / 閉包に動的インポート構文（`__import__` / `importlib`）が現れる / 閉包が空 ⇒ 一律**コード面の一塊に退回**；さらに**実行時完全性の判定**——新品のインタプリタでその派生を実際に走らせ、その間に import された `core.*` がすべて閉包内になければならない（静的解析の見落としはその場で赤になる）。決定的な証拠：`desktop/src/core/terminal.py` を変えた後、キーを替えるサイト数は **9/9** から **0/9** に下がった。

デーモン側にもう一箇所「自滅」があったので直した：「コードが版を替えた」と判定するとき `core.*` を一塊で外して再ロードする（古いコードを走らせない保証）ため、新しいモジュールの常駐コーパス層が空になっていた——現在は版替えの前に取り出し、版替えの後に戻す（層にあるのはリポジトリの事実で、コードとは無関係）。エンドツーエンド：**1 行のコード変更後の最初の重いコマンド 2609 → 870 ms**（もう一度変えると 440 ms）。

**覚えておくべき二つの境界**：① コールドプロセス（デーモンなし）は広い面キャッシュを**使わない**——`nf score` ~1.9 s、`nf conformance` ~2.3 s で、接続前と一致（読み値を速度と引き換えにしない）；② コードを**データ**として監査する派生（純度 / ラダー / 縦深集約）はコード変化後に**必ず**再計算する——それは真の依存であり、浪費ではない。

**境界（必ず知るべき）**：`desktop/src`/`scripts` 下のファイルをどれか変える ⇒ コード面がキーに入る ⇒ すべてのディスク上の派生条目が一斉にキーを替え、**次の重いコマンドは全量再計算を 1 回支払う**（実測 ~4.9 s）。これは「コード面をキーに入れる」という既存の規律の代価である：再計算を選び、旧アルゴリズムが算出した勘定を新しい勘定として扱わない。判定は `test_conformance_scan.DerivedResultCacheTest`（8 サイト、表駆動；「読んだ件は宣言された入力面内に落ちなければならない」という一条は、スキャナに新しい読み取りを足すと先に赤くなる——本ラウンドではその場で 2 件の宣言漏れを捕まえた）。

```sh
nf daemon start                      # デーモンを起動（バックグラウンド；127.0.0.1 のみ束縛 + ワンタイムトークン）
nf daemon start --watch              # 別途：ディレクトリ監視 + 読み取り専用コマンドのレスポンスキャッシュ（木が不変なら応答全体を再利用）
eval "$(nf daemon shell-init bash)"  # 現在の shell に導入：子プロセスゼロのクライアント（真のミリ秒級）
nf daemon bench                      # 上表を再走（--json で機読）
nf daemon stop                       # 停止：直ちに python 直接実行へ戻り、可用性は何も変わらない
```

規律（全リポジトリと一致、いずれも判定あり）：

- **加速のみ、意味論は変えない**：デーモンの `(exit, stdout, stderr)` は**真の子プロセスの直接実行とバイト単位で同一**（`test_daemon` がコマンドごとに照合）。
- **熱いプロセスは陳腐化してはならない**：要求ごとに**パスキー**のキャッシュを空にする（`pack_combo` プロファイル / `registry_loader` レジストリ）、**内容キー**キャッシュは保持する（フェンス付き YAML、参照度普查——キーが内容そのものなので天然に陳腐化しない）；別途 `core/scripts` の**ソースフィンガープリント**で一塊の再ロード可否を判断し、古いコードで応答することは絶対にない。
- **安全境界**：`127.0.0.1` のみ束縛（外網を放行するスイッチは**ない**）+ ワンタイムトークン（ループバックは信頼境界ではない）+ リクエスト 1 MiB 上限；常駐/自己参照コマンド（`serve` / `shell` / `terminal` / `lsp` / `daemon`）はデーモン内で**実行拒否**され、拒否後もデーモンは生存する。**別名も常駐面も一視同仁**（2026-10-01 修正）：`terminal` は `shell` の別名、`lsp` は常駐 stdio サービスで、以前は拒否表になかった ⇒ デーモンのファストパス経由だと**無言でゼロ出力のまま exit 0** し、直接実行では本当にサービスが起動していた。
- **可退避**：どの段階が成立しなくても（状態ファイルなし / bash なし / 接続不可 / プロトコルヘッダ不正）ランチャーは**静かに python 直接実行へ退避**する。

```sh
python scripts/nf.py shell --exec "nf doctor" --no-banner
python scripts/nf.py shell --exec "/zone 5" --json --no-banner
python scripts/nf.py shell --file tour.nf                    # スクリプトファイル（# コメント / 空行スキップ / 行内 ; で再分離）
python scripts/nf.py shell --file tour.nf --json             # 同一実行チェーンの機械面
```

- `--exec` は `;` で区切る（改行も区切りとして数える）、`--file` は 1 行ずつ実行する；両者は**同じ実行チェーンを共有**する（同じ Session / 索引 / 書き込みゲート）。ゆえに「ターミナルで打てるもの」と「スクリプトで走れるもの」は常に同じ意味論になる。
- 1 条ずつ実行し、1 条ずつ `kind/exit` を出す；終了コード = 各条の最大値。
- `--json` は `{"kind": "nf-shell", …}` を出力し、1 条ずつ記録する（argv / exit / out / err を含む）機械面。
- `--no-banner` は冒頭バナーを外す（ログ場面）。

## 境界

- **全画面 TUI ではない**：NF の対話面は意図的に「行ごとの読み書き」に留める——リダイレクト可、diff 可、CI に入れる；全画面 TUI はターミナル能力への結合とサードパーティ依存を持ち込み、core の「サードパーティ依存ゼロ」レッドラインと衝突する。
- **第二のコマンド面ではない**：ターミナルは業務ロジックを複製しない。コマンドの真源は常に `scripts/nf.py` の argparse 面である。
- **新しい GUI/新しいシェル**：本ファイルの範囲外；`STRATEGY.md` §四と裁定記録により、作者の新たな裁定を経てから別途立項する必要がある。
